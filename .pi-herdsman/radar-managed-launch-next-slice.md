# Radar managed-child launch: executable next slice

## Decision

Port **fresh managed-worker launch and child binding first**, while keeping Herdsman as the assignment owner. Do not include retained-worker resume/replacement or automatic `child.close` in this slice. Radar `spawn` is a real, supported operation; missing Herdsman client plumbing is implementation work, not a Radar protocol gap. However, the currently published parent registrations do not carry a location, so this exact parent must first be supplied with a truthful current pane location from the process's trusted startup environment. No inferred pane IDs, labels, session-to-pane lookup, or registry location fabricated from unrelated observations.

A spawned child is not ready for assignment merely because spawn completed or its token bound. Readiness requires both (a) the exact child registration bound to this spawn edge, and (b) a **fresh, child-authored startup acknowledgment** for the expected run, owner, label, child session and launch generation, written only after Herdsman startup initialization succeeds. Current code has no such explicit acknowledgment; add one in Herdsman.

## Verified Radar contract

Contract is v1 at `/home/saurabhj/Projects/dev/agent-radar/docs/control-plane.md` and `docs/agent-registration.md`; physical adapter guarantees are in `docs/mux.md`.

- `agent.register.location` is optional and contains backend/optional instance/workspace/tab/pane strings (`src/control_plane/registry.rs:75-101,195-225,258-291`). It is registration data, not a live mux observation or verified process-to-pane binding.
- `execute_spawn` loads the **exact** `params.parent` registration and its fresh matching non-null `agent.context`, then obtains `parent.request.location.pane`; if missing, it refuses. It does not find a pane by process, session, name or alias (`src/control_plane/server.rs:2960-3067`). Spawn splits right, unfocused, under that pane and launches via adapter (`:3109-3252`).
- Therefore caller must register current exact location (or the system must add a separately specified authoritative location update/read flow). Current `radar-publication.ts` builds registration from source/owner/run/label and process birth but no location (`:1228-1248`); current types support location but adapter does not populate it (`radar-client.ts:75-99`). The parent-location problem is not a Radar lookup gap: registration location is the parent selector and is merely a claim unless Herdsman supplies trusted current identity.
- Spawn takes exact parent agent UUID + `parent_session_id`, resolved executable, literal argv, optional absolute cwd and env overlay. Requires `creation` + `launch`; with cwd/env also `child_launch_context_v1`. Daemon verifies fresh session context on exact parent before effects. Herdr refuses unrepresentable launch arguments before create. The env is overlay, and `PI_RADAR_SPAWN_TOKEN` is reserved, private, one-use. Child presents the captured token in its own `agent.register`; binding is single-use and exposes exact `bound.agent_id` from `spawn.get`/`spawn.list`. Never correlate by session, alias, pane, or label. (`control-plane.md` Durable operations; `agent-registration.md` Spawn operation/topology; `mux.md` Launch and binding.)
- Unknown spawn outcome must be reconciled by the same request UUID/readback; never retry with a new ID or fall back to Herdr. A launch refusal after create can leave a named pane/edge. `child.close` can only close the exact bound spawn child after fresh foreground identity proof; it reports pane closure only, not process exit. No operation supplies process stop/resume/restart. (same references.)
- Placement is fixed to nonfocused right split of registered parent pane. There is no arbitrary existing pane, new tab/workspace, or caller-selected anchor for managed spawn (`mux.md` Physical operations).

## Current Herdsman path and readiness evidence

- Parent execution identity: process-local Radar registration is established by `createRadarExecutionAdapter`; its options carry managed owner/run/label and process birth claim. It reports session context on Pi `session_start`; `RadarPublication.binding()` gives managed child subject identity, not parent location (`radar-execution.ts:33-60,124-145,199-207,247-280`; `radar-publication.ts:333-341,1228-1248,1280-1308`; `index.ts:19300-19412`). Add a narrow accessor for this process's registered `agent_id` and location only if that location is populated from trusted current host facts.
- Current child launch preparation resolves command, agent args, target cwd and all Herdsman env entries in `prepareManagedWorkerLaunch` (`index.ts:3412-3580`). These are directly mappable to Radar `executable`, `argv`, `cwd`, `env` overlay after treating executable as resolved and separating executable from argv. The existing `childLaunchPlan` handles newline args with a temporary script (`herdr.ts:1779-1818`); Radar spawn does not support this fallback and Herdr adapter refuses newline/control and overlong commands. Prefer preflight refusal; do not place command/script in `input` or silently alter argv.
- Current bootstrap sets managed child environment including mailbox/run/owner/session/label/workspace/definition/brief/cwd fields (`index.ts:3412-3495`); it does not pass Radar spawn token through this preparation. Search of `pi-herdsman` source finds no `PI_RADAR_SPAWN_TOKEN` or `spawn_token` handling. Add token capture at process initialization, remove it from `process.env` immediately, and include only in private registration request. Keep token in bootstrap memory only as long as exact registration retry requires; never mailbox/log/metadata.
- Current `radar-publication` stores immutable subject registration and a sidecar binding keyed by run/owner/label. That sidecar is written from the child process's registration (`radar-publication.ts:1260-1309`) and `index.ts:938-944` reads it for owner assignment targeting. It is not proof that this process is the child of a particular spawn request. Persist exact spawn request ID alongside exact bound child agent ID (private Herdsman record), and validate against Radar `spawn.get` rather than replacing identity with alias.
- Worker `session_start` does useful initialization: constructs candidate managed identity, checks mailbox consistency, validates/loads agent definition, writes state under assignment lock, recovers agent runtimes, sets `agentControllerReady` and `initialized`, starts scanner/watch/pump (`index.ts:17648-17870`). But the state written (`ManagedAgentState`, `mailbox.ts:28-57`) has no launch-generation/startup-ack field. Existing readiness is external Herdr registration/alias/pane checks in `herdr.ts:1484-1567`; this is not a child-authored ack for required hooks. `RadarExecutionAdapter` publishes generic Pi activity (`session_start` idle/working, `agent_start` working; `radar-execution.ts:247-280`), not “Herdsman initialized and can accept an assignment.” Radar registration/binding or ordinary mailbox identity fields alone are insufficient.
- Add a dedicated launch-generation nonce to child bootstrap env and mailbox identity/ack. At the end of successful `session_start`, after state write and required controller/runtime initialization, atomically write/advance `startupAck` containing generation plus runId, ownerSessionId, label, workspace, pane/location identity and Pi session UUID. Parent wait requires exact values and a strictly fresh ack tied to this new nonce, not a prior mailbox file or mere field presence. If readiness fails, timeout/unknown remains unresolved; do not make assignment success claims or close based on it. A dedicated ack generation avoids trusting stale state; existing `updatedAt` is not a sufficient generation proof.

## Minimal implementation slice

1. **Exact parent identity and location precondition** (`radar-execution.ts`, `radar-publication.ts`, narrow process adapter): expose the current process's stable Radar agent ID and ensure its immutable registration carries the exact pane location obtained from trusted current Pi/host initialization (likely child/lead env coordinates today). Verify those coordinates belong to this process using existing startup ownership checks; do not synthesize a location or call `observe` then claim it as registration identity without an explicit verification rule. `agent.context` already publishes exact current Pi session UUID; parent spawn must use that same session.
2. **Typed spawn transport** (`radar-client.ts`): add typed `spawn`, `spawnGet`, `agentGet` as needed; negotiate protocol/capabilities, decode durable request + edge, retain UUID, classify unknown honestly. Pass resolved executable, argv, target cwd and only necessary env overlay. Ensure Herdr reporter flags/extension installation are not passed: Herdsman owns app readiness and Radar registration, not native Herdr reporter.
3. **Child token/bootstrap** (`radar-publication.ts`, `index.ts`): consume `PI_RADAR_SPAWN_TOKEN` once before it can leak; retain for agent.register exact retry; register child with private spawn_token. Child's own publication registration creates its `agent_id`; parent uses `spawn.get.spawn.bound.agent_id` exactly and compares with child-side publication binding before durable child record. Persist exact spawn request id, bound ID and startup-generation nonce in private existing child-run record/mailbox, preserving current owner/run/label identity semantics.
4. **Fresh readiness acknowledgment** (`mailbox.ts`, child `index.ts`, parent launch orchestration): implement as above, parent waits for exact fresh generation + identity after token binding. Keep readiness distinct from assignment mailbox request delivery and from execution `activity` publication.
5. **Narrow cutover target:** fresh managed-worker launches only in the already-supported parent-pane right-split placement. Keep retained worker reuse and cleanup paths unchanged until a later slice. Since future `child.close` is limited to Radar-spawned/token-bound children and only closes panes, keep existing owner-side preflight and completion/result/assignment rules; do not automatically convert close or infer process exit from close. The task authorizes spawn prerequisite for later child.close, not redefining close semantics.

## Blockers versus implementable now

**No Radar contract blocker** for supported parent-right-split fresh launch with cwd/env, exact token binding, and Herdsman-authored readiness. The integration work is absent in Herdsman and is authorized.

**Hard product/runtime precondition:** parent registration must supply a truthful current `location.pane`. Current publisher omits location, and current env apparently retains `HERDR_PANE_ID` for workers but Herdsman must establish its trust and host-neutral replacement before full Herdr removal. If a reliable exact parent pane fact is not available for a caller, that caller cannot use spawn; do not fall back to names/session search. Pane identity may be backend-specific/opaque; later backend-neutral operation requires an explicitly supplied location compatible with selected Radar backend. The new tmux backend requires named server context and there is no current Herdsman backend selector/wiring; first implementation can target current Herdr-backed daemon only, with tmux adoption deferred until location/server binding is designed.

**Capability/contract gaps:** placement beyond exact parent right split; process stop/resume/restart/replacement; universal process-exit proof; startup readiness API is not a Radar gap (Herdsman owns it). `child.close` is implementable only after spawn binding + claimed process birth identity + current exact foreground evidence; unavailable evidence refuses. It is not part of the launch/readiness success claim.

**Operational:** Radar daemon is separately started and not supervised by Herdsman (`control-plane.md` Start and select). Runtime daemon ownership/startup wiring must be chosen before claiming deployment cutover. No live launch performed in this investigation.
