# Herdr removal migration scope

## Summary

This is an inventory and proposed migration plan only; no production files changed. Radar's v1 daemon is a mux control plane, not an agent launcher or supervisor. Current `radar-client.ts` is registry-oriented; mux migration requires extending it. The largest blockers are launching a process in the new pane without `spawn`, obtaining the identity/process evidence used by lifecycle safeguards, replacing direct process stop, and parity for workspace/tab topology, session inspection and lifecycle events.

## Evidence and completeness

The primary direct adapter is `pi-herdsman/extension/herdr.ts`: `runHerdr` invokes the Herdr binary via `pi.exec` (321-378); inspection has a separate direct `pi.exec("herdr", ...)` (223-237). The consumer is `extension/index.ts`. Exact `runHerdr`/`pi.exec("herdr")` searches were scoped to `pi-herdsman/extension`; broader `herdr` search included package scripts/docs/wiring and surfaced additional references. Search results are not a machine-verified count of all direct runtime invocations across every test and deployment file. Counts below are counts of call expressions visible in relevant implementation groups, not behavioral request counts; shared helpers multiply at runtime. Tests, smoke scripts, docs, installer, Docker and package/Nix inputs remain separate migration/removal work.

## Herdr-derived facts and dependency

- Alias/name is run-scoped identity used by destructive control resolution and ownership checks (`index.ts:3626-3698`; `herdr.ts:485-491`, `:1512-1529`). Radar `agent_id` is a UUID and registration includes source/incarnation/owner/run/label; no mutable Herdr alias contract. Herdsman must preserve mapping itself or adopt a new identity design (decision required).
- Pane/workspace/tab IDs and containment are used in startup placement and close/rollback proof (`herdr.ts:505-520`, `:1024-1435`, `:2238-2439`). Radar `observe` returns normalized FleetObservation; create can return runtime-reported ID. Compatibility of identifier formats and full tab/workspace topology needs mux contract confirmation (`mux.md`).
- Foreground shell/process PID/group/argv and exact session evidence are used to prove ownership and safe close/rollback (`herdr.ts:38-48`, `:527-586`, `:1835-1862`, `:2238-2344`). Radar `process_info` is foreground evidence and `child.close` uses stronger procfs birth identity only for Radar spawn edge children. No general Herdr PID/group snapshot equivalent; direct process stop remains absent.
- Agent status/session comes from Herdr agent records and reporter (`herdr.ts:1570-1614`, `index.ts:2395`). Radar `report` schemas can carry state/session/metadata and registry can store registration/context, but no claim that Radar observes arbitrary agent sessions or generates terminal state. The protocol says Radar does not infer ownership of arbitrary mux resources.

## Herdr-specific configuration and distribution surface

Evidence from scoped `pi-herdsman` search: `extension/herdr.ts` uses `HERDR_WORKSPACE_ID` (`:437-440`), `PI_HERDSMAN_CHILD_COMMAND` (`:1729`), reporter extension under Pi agent dir (`:122-130`), and executes binary `herdr` (`:331`, plus `:223-235`). `extension/index.ts` has Herdr status/config/integration calls and user guidance (e.g. `:2213`, `:2435`, `:8689`, `:8778`). Other discovered migration surfaces: `pi-herdsman/package.json:37,52` runtime dependency/version; `install.sh:6,71-150`; `Dockerfile:18,78-85,114-132`; `docker/entrypoint.sh:90`; `scripts/smoke.mjs:38-44,1151-1397`; README installation/runtime guidance. Tests include `extension/herdr.test.ts`, `extension/installer.test.ts`, controller/smoke tests. These are likely removal/update targets after runtime migration; do not remove install/runtime wiring until the direct runtime boundary and deployment contract are replaced.

## Existing Radar seam

`extension/radar-client.ts` exposes registry transport/types and `childClose`, but not mux calls (`RadarClient` at lines 1-15, 220-301; client operations from 315 onward). It already handles trusted socket path, one-call UUID envelopes, timeouts and registry negotiation. Extend it behind an adapter boundary rather than importing direct socket code throughout `index.ts`. Mutations need fresh UUIDs and durable request reconciliation: Radar says timeout/disconnect after a write is ambiguous; never automatically retry uncertain mutations, including via direct adapter (`control-plane.md`, Transport and envelope; Durable operations).

## Ordered smallest shippable slices

1. **Mux observation adapter**: add typed Radar `ping/observe/output/process_info` client methods and capability negotiation; adapt read-only inventory consumers. Blocked on confirming exact normalized FleetObservation fields against `mux.md`; no Herdr agent/worktree equivalence.
2. **Create/focus/input durable wrappers**: typed methods and outcome model with caller-supplied UUID/reconciliation; migrate one isolated pane-create/focus/input path. Blocked for launch-specific create cwd/env/ratio and process startup semantics. Never retry unknown input.
3. **Launch without Radar spawn**: `create` + `input` launch script + registration/readiness observation; isolate from rollback and require operator-visible unresolved state on unknown input. Blocked on contract for launch environment transport through create/input and verified registration-to-pane binding; do not use Radar spawn per scope.
4. **Report publication**: map Herdsman-owned state/session/metadata to `report`, replacing reporter-extension dependency only where values are publisher-owned. Blocked on enumerating current reporters and which publisher owns each fact; report is not generic Herdr state merge.
5. **Close and rollback**: migrate only confirmed unmanaged mux closes with frozen identity; preserve manager-authorized managed cleanup path. Blocked for existing Herdr-launched managed children: Radar child.close eligibility requires daemon spawn edge/token, and v1 has no process stop.
6. **Lifecycle/recovery and distribution cleanup**: replace Herdr event watcher with polling or await Radar event contract; remove binary, env, reporter, installer/Docker/package/Nix/docs/tests only after no runtime callers. Blocked on event/process-exit/state contract and product deployment decision for Radar daemon lifecycle (Radar does not start daemon).

## Open questions / risks

1. What exact Radar inventory fields and pane ID guarantees does mux integration contract promise, especially workspace/tab identity, cwd and layout?
2. What replaces safe process stop and restart for existing managed children if Radar will not supervise them and spawn is excluded?
3. What establishes a registration's pane/process binding for children launched via create+input, without a Radar spawn token?
4. Which runtime component starts/owns the separate Radar daemon? Protocol explicitly says Radar does not start it.
5. Can process-info and output polling safely provide current startup readiness and process ownership, or is a new capability needed?

## First files to open

Start with `pi-herdsman/extension/herdr.ts` (direct boundary, launch and ownership proofs), then `pi-herdsman/extension/radar-client.ts` (existing transport seam), `pi-herdsman/extension/index.ts` (consumers and identity semantics), and the canonical Radar `docs/mux.md` plus `docs/control-plane.md` (backend contract and method semantics).
