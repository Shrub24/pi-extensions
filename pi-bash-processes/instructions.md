## pi-background-tasks — `bg_task`

Model-facing Bash commands are managed from process start. If a command exceeds the foreground wait (20 seconds by default), Bash returns a `Running` task ID and keeps executing in the background. Running is not success: do not use its output or artifacts yet, and continue only work that is independent of the result. If nothing independent remains, finish the turn with a brief waiting status and go idle; completion (or timeout) wakes you in a new agent turn with the output tail — that wake is the delivery mechanism, not a suggestion. A caller that cannot end its response before it has the result — a child or headless session, for example — should use the bounded wait this mode's own guidance describes, when it offers one.

`bg_task` starts, inspects, and stops those tasks. Use it instead of `nohup`, `&`, `disown`, or foreground polling loops. This mode's own tool guidance lists which actions exist here and how to await a result in this session; do not assume an action is available because another mode has it, and do not repeat `list`/`get` calls in a polling loop.

Read a task's result through the declared operation, never by reading a log file. A result is certified only once the manager has settled the task's capture, so a plain `cat`/`tail`/`grep` of a log file reports bytes without settling anything and without canceling the task's completion wake. A `get` hands the result over and acknowledges its completion notification exactly once; a full read hands over the complete immutable snapshot, and an oversized one is preserved in a readable artifact rather than truncated. A read that cannot certify a complete capture says so and acknowledges nothing.

Every task also gets a soft reminder (default 10 minutes, `softTimeoutMs` per spawn), scheduled from the last successful review rather than from output activity. A soft reminder is not an exit and stops nothing: it reports elapsed time and output and asks you to continue, inspect the result, or stop the task. The hard `timeoutSeconds` is an absolute process-lifetime ceiling — no read, listing, reminder, or legacy soft reset extends it — and a task with no configured hard limit never acquires one through retrieval.

Stopping is confirmed or explicitly unconfirmed. A `stop` waits only for the bounded termination/finalization procedure, returns the real outcome under the same task ID, and leaves the result retrievable; a stop that cannot confirm termination says so and leaves the completion obligation outstanding. Sending a signal is never reported as a stopped task.

Wakes: exits notify by default (`notifyOnExit`); `notifyOnOutput` + `notifyPattern` wake on matching new output (`notifyMode`: `always` | `transition` | `first-match-only`). Multiple exits in the same window arrive batched; a missed wake (crash, restart) replays at most once. Stop turn-scoped tasks you no longer need before finishing the turn.

The `pi-bg` CLI is on the PATH of managed commands and speaks to this session's own endpoint: `pi-bg get <task-id> [--output]` writes the result, or the complete immutable snapshot, to stdout with metadata on stderr; `pi-bg list` lists tasks; `pi-bg stop <task-id>` stops one and reports the confirmed result. A handle belongs to the session that created it and another session's handle is refused. Retained tasks and their artifacts expire after the configured retention, and an expired handle reports an explicit error rather than an empty result.

Do not trim a command's output yourself: no `| tail`, no `| head`, no `2>/dev/null` on a command whose result you need. Output too large for the transcript is bounded for you and saved in full to a file the result names, and a background task's log keeps everything; a trim discards the part you may need, hides which stage failed, and usually forces a re-run. Run the command plainly and read the saved output (or `bg_task get output:"full"`) when you need more. Managed shells run with `pipefail`, so a failing pipeline stage fails the command rather than hiding behind the last stage's exit code.

Resource controls (opt-in setting, off by default): heavy tasks can run through a `systemd-run` transient service or a `nice`/`ionice` fallback while preserving log capture, wakeups, timeouts, and `/bg:stop`.
